# Handy-Cloud 实时流式转录规格说明书 (Gemini Live API)

## 问题说明

从桌面语音转写用户的实际使用体验出发，当前主要存在以下体验痛点：

1. **录音与出字延迟割裂**：当前云端转录采用“批处理”模式，用户必须按住热键说话、松开按键后等待数秒音频整体上传与云端返回，才能看到文本输出。在长句或快节奏打字场景下，缺乏实时反馈，用户无法即时确认自己的发音是否已被正确捕获；
2. **离线实时模型对硬件要求苛刻**：虽然系统支持部分本地流式模型，但需要设备具备较高算力（占用大量显存/内存与持续高 CPU 负载），轻薄本或缺乏强劲显卡的设备无法享受边说话边实时出字的流畅打字体验；
3. **网络抖动下的转录可靠性风险**：在弱网或网络中断场景下，若缺乏健全的流式降级与重试机制，用户可能丢失已录入的整段语音。

## 解决方案

1. **引入 Gemini Transcribe Live 实时流式语音转写**：接入 Google 官方最新的专用流式转写大模型，建立双向全双工长连接，边说话边向云端推送音频分片，实现毫秒级打字机出字体验；
2. **复用原生两级悬浮窗字幕渲染**：直接复用系统已有的“稳定前缀 + 实时推测后缀”两级文字显示架构，用户说话时动态更新推测词，停顿或分句时权威确认，并带有闪烁光标与波形联动，零新增前端认知成本；
3. **全局网络代理穿透与隧道支持**：长连接全面接入现有的全局网络代理管理器，无缝支持企业与国内常见的 HTTP CONNECT 与 SOCKS5 代理隧道；
4. **无感容灾回退机制**：本地在流式推流的同时始终完整保留该次录音的原始音频；一旦遇到长连接异常中断或超时，系统无感自动回退至云端批处理模式，确保用户语音资产绝对不丢失。

## 用户故事

1. 作为日常桌面文字录入用户，我希望在按住热键说话时屏幕悬浮窗能像打字机一样实时蹦出文字，以便随时确认识别效果并大幅降低等待焦虑。
2. 作为使用轻薄本的用户，我希望无需下载数 GB 本地大模型、不占用本地独立显卡算力，就能享受与高性能设备一致的实时流式听写体验。
3. 作为长句听写用户，我希望在说话停顿时已确认的字词保持稳定、后续推测字词平滑滚动，以便获得连贯、不晃眼的视觉阅读体验。
4. 作为处于公司内网或代理环境的用户，我希望实时流式长连接能够自动沿用全局设置的代理通道，以便在受限网络下稳定使用云端实时转录。
5. 作为口误或有语气助词的用户，我希望实时流式识别能自动去除“嗯、啊、这个”等口癖并自动规整标点符号，以便输出开箱即用的整洁书面文本。
6. 作为对网络稳定性有担忧的用户，我希望在网络突发抖动导致流式连接中断时，系统能自动将录音回退到常规云端批处理完成转写，以便不会因网络闪断而白说一段话。
7. 作为热键录音用户，我希望在松开录音快捷键时系统能立即完成末尾分句规整，并将最终文本直接自动粘贴到当前活跃应用的光标处。

## 实现决策

- **转写路由架构扩展（Streaming Provider Trait）**：
  在转写路由层抽象出统一的流式提供者接口与流式会话生命周期对象。转写路由器聚合本地流式引擎与云端流式服务商，根据当前生效的转写配置统一判定流式支持状态并调度流式会话。
- **流式会话生命周期与协议状态机**：
  流式会话严格遵循四阶段状态机：
  1. _建立阶段_：通过代理隧道发起安全 WebSocket 握手，建立后发送配置握手帧（指定模型名称、音频模态为纯文本、启用智能去口癖与标点规整模式）；
  2. _推流阶段_：持续接收麦克风采集的音频采样，按 100 毫秒（1600 采样）为周期缓冲，转换为标准 16 位单声道 16kHz 无损 PCM 格式并进行 Base64 编码，封装为实时输入数据帧持续发送；
  3. _接收阶段_：独立监听服务端下行事件，将收到的毫秒级推测片段映射为悬浮窗暂态文本，将分句权威文本累加至稳定前缀，触发系统事件广播；
  4. _收尾阶段_：录音停止时向服务端发送音频流结束标记，等待服务端返回最终分句确认，返回完整文本并优雅关闭连接。
- **全局代理通道复用**：
  WebSocket 长连接复用全局网络管理器的代理策略。对于 HTTP 代理，采用标准 HTTP CONNECT 建立 TCP 隧道后再进行 TLS 握手；对于 SOCKS5 代理，先完成 SOCKS5 握手再进行 TLS 封装，确保代理穿透的兼容性。
- **两级字幕映射（零前端改动契约）**：
  将服务端的 `interimInputTranscription` 映射为悬浮窗的 `tentative` 字段，将 `inputTranscription` 映射为 `committed` 字段。完全沿用现有的 `stream-text-event` 与 `stream-phase-event` 事件定义，前端打字悬浮窗代码保持 100% 零修改。
- **双轨录音与自动降级容灾（Dual-Track Failover）**：
  录音期间，本地音频管理器一如既往地将完整音频采样收集在内存中并写入本地历史 WAV 文件。若流式会话在收尾前发生超时、断线或致命错误，系统自动捕获异常，无感调用已有的云端批处理转录接口处理该段完整音频，保障转录成功率。
- **配置与模型枚举扩充**：
  在转录模型设置中，将流式专用模型作为高亮选项列出，与现有的云端批处理模型并存。当用户选择流式模型时，录音前置逻辑自动激活流式悬浮窗与音频旁路路由。

```typescript
// 核心配置与事件 Schema 示意（源自已有架构）
interface StreamTextEvent {
  committed: string; // 稳定前缀
  tentative: string; // 易变推测后缀
}

interface StreamPhaseEvent {
  phase: "listening" | "working";
  kind?: "transcribing" | "polishing";
}
```

## 测试决策

- **好测试的判断标准**：
  只测试外部可观察行为（如流式会话交付的稳定与暂态文本更新、最终输出的文本内容、网络断开时的自动回退行为、事件总线广播的阶段变迁），严禁测试内部私有缓冲区切片索引、内部锁竞争等实现细节。
- **外部验证切入点**：
  1. _转写路由流式会话接口与事件总线_：作为最高层级的测试验证入口，通过传入音频流与事件监听器，直接检验整个推流、两级文本产出与收尾全生命周期；
  2. _本地模拟 WebSocket 服务端_：在测试环境下启动轻量级本地测试服务端模拟云端双向报文交互，用于确定性地验证鉴权握手、数据切片编码正确性以及模拟网络异常断开场景下的自动降级容灾。
- **待验证的核心行为**：
  - 100ms PCM 帧的格式转换与 Base64 编码准确性；
  - 收到推测事件与确认事件时两级文本的累加与更新状态；
  - 发送音频结束标记后服务端最终分句的正确收尾与剪贴板文本返回；
  - 模拟网络超时或连接中断时，系统无缝自动降级至批处理并成功产出文本；
  - HTTP CONNECT 与 SOCKS5 代理握手建立逻辑正确性。
- **代码库中可参考的同类测试**：
  参考代码库中现存的 `BatchTranscriptionProvider` 契约测试、网络管理器的连通性测试以及本地流式 Worker 的生命周期测试。

## 不在范围内

- 为云端流式引入对话式双向语音生成（即仅使用文本转写输出模态，不启用大模型的语音播报回响）；
- 破坏或改动本地现有基于 C++ 推理库的流式实现；
- 在前端重新发明一套独立的流式字幕 UI 组件（强制复用现存成熟的悬浮窗）。
